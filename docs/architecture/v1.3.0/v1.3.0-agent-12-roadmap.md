## 1. Executive Summary

### 1.1 Scope

clnrm v1.3.0 delivers **production-ready Weaver live-check integration**, transforming telemetry validation from "infrastructure exists" (v1.2.0) to "telemetry proves features work" (v1.3.0).

**Core Deliverable**: Weaver `registry live-check` becomes the **single source of truth** for feature validation, replacing traditional tests as the primary validation mechanism.

### 1.2 Timeline

- **Development Duration:** 10 weeks (50 working days)
- **Alpha Release:** End of Week 5
- **Beta Release:** End of Week 8
- **v1.3.0 GA Release:** End of Week 10

### 1.3 Risk Level

**Overall: MEDIUM**

- **High Risk Areas:** Weaver process lifecycle (zombie processes, cleanup)
- **Medium Risk Areas:** Port allocation races, OTLP flush timing
- **Low Risk Areas:** TOML parsing, backward compatibility

**Mitigation:** Extensive integration testing, RAII patterns for cleanup, atomic port locking.

### 1.4 Confidence

**Implementation Complexity: 7/10**

- **Known Territory:** Port management, TOML config, process spawning (v1.2.0 foundation)
- **New Territory:** Type-safe state machines, streaming validation, 80/20 mode
- **Confidence Boosters:** 6 detailed architecture documents, clear API contracts

### 1.5 Dependencies

**External:**
- Weaver binary (v0.8.0+) - Install from GitHub releases
- Docker/Podman (for testcontainers)
- Rust 1.70+ (async/await, PhantomData for type-safe states)

**Internal:**
- opentelemetry-otlp (0.15.0+)
- tokio (1.28.0+)
- nix crate (Unix signals)
- serde (TOML parsing)

## 3. Risk Assessment

### 3.1 High Risk Areas

#### Risk 1: Weaver Process Management (Zombie Processes, Cleanup)

**Probability:** MEDIUM (30%)
**Impact:** HIGH (blocks all validation)
**Risk Score:** 0.30 * 10 = 3.0 (MEDIUM-HIGH)

**Symptoms:**
- Orphaned Weaver processes consume ports
- Tests fail with "port already in use" after crashes
- Cleanup fails on CI runner restart

**Mitigation Strategy:**
1. **RAII Pattern**: Use Drop trait for automatic cleanup
2. **Startup Cleanup**: Run `pkill weaver` on every test start
3. **Timeout-Based Force Kill**: After 10s, kill -9 if graceful shutdown fails
4. **File-Based Locks**: Track process ownership via lock files
5. **Health Monitoring**: Detect zombie processes via PID check + HTTP health

**Testing:**
- Stress test: Kill Weaver mid-execution (SIGKILL)
- Stress test: Panic during orchestrator.start_weaver()
- Verify lock files removed on crash

**Contingency:**
- If cleanup unreliable: Add Docker-based isolation (run Weaver in container)
- If still fails: Document manual cleanup procedure in runbook

---

#### Risk 2: Port Allocation Race Conditions

**Probability:** MEDIUM (25%)
**Impact:** MEDIUM (intermittent CI failures)
**Risk Score:** 0.25 * 7 = 1.75 (MEDIUM)

**Symptoms:**
- "Port already in use" errors in parallel CI jobs
- TcpListener.bind() succeeds but Weaver fails to start
- Port conflicts between OTLP and admin ports

**Mitigation Strategy:**
1. **Atomic Locking**: File-based locks (flock) prevent races
2. **3-Tier Fallback**: 40 ports total (4317-4327, 5317-5327, 6317-6337)
3. **Health Check Validation**: Verify Weaver actually bound port
4. **Retry Logic**: Retry port discovery once on failure
5. **Job Isolation**: Allocate port ranges per CI job (job_index * 100)

**Testing:**
- Stress test: 20 parallel Weaver startups
- Verify: Zero "port in use" errors in 1000 iterations
- CI test: GitHub Actions matrix with 10 parallel jobs

**Contingency:**
- If 40 ports insufficient: Add Tier 4 (7317-7337) dynamically
- If still conflicts: Serialize Weaver startups via lock file

---

### 3.2 Medium Risk Areas

#### Risk 3: OTLP Flush Timing (Telemetry Lost Before Shutdown)

**Probability:** MEDIUM (20%)
**Impact:** MEDIUM (false positive validation failures)
**Risk Score:** 0.20 * 6 = 1.2 (MEDIUM)

**Symptoms:**
- Conformance report shows sample_count < expected
- Last test spans missing from validation
- "Zero telemetry received" errors

**Mitigation Strategy:**
1. **Explicit Flush**: Call `otel_guard.flush_all()` before stop
2. **Sleep Guard**: Wait 500ms after flush for network drain
3. **Retry Logic**: Retry OTLP export on transient failures
4. **Backpressure Handling**: Configure 5 retries with exponential backoff
5. **Inactivity Timeout**: Set to 120s (long enough for flush)

**Testing:**
- Integration test: Emit 1000 spans → verify all in report
- Stress test: Fast test completion (< flush interval)
- Measure: P99 flush latency (must be < 500ms)

**Contingency:**
- If unreliable: Increase sleep guard to 1000ms
- If still fails: Add explicit OTLP ACK confirmation

---

#### Risk 4: Configuration Validation Gaps

**Probability:** LOW (15%)
**Impact:** MEDIUM (confusing error messages)
**Risk Score:** 0.15 * 5 = 0.75 (LOW-MEDIUM)

**Symptoms:**
- Invalid TOML accepted, crashes at runtime
- Conflicting config values (e.g., otlp_port == admin_port)
- Missing registry path discovered too late

**Mitigation Strategy:**
1. **Schema Validation**: Validate all constraints in WeaverConfig::validate()
2. **Early Validation**: Parse and validate TOML before Weaver startup
3. **Clear Error Messages**: Provide path to fix (e.g., "Registry not found: /path. Create with: weaver registry init")
4. **Default Values**: Sensible defaults for all optional fields
5. **Pre-Flight Checks**: Verify Weaver binary installed, registry exists

**Testing:**
- Unit tests: 20+ invalid config scenarios
- Error message clarity: Manual review by non-expert
- Integration test: Run with missing/invalid config

**Contingency:**
- If validation insufficient: Add `clnrm validate-config` command
- Add JSON schema for IDE autocomplete

### 3.3 Low Risk Areas

## 8. Rollback Strategy

### 8.1 Rollback Triggers

**When to roll back:**
1. **Critical Bug** - Data loss, security vulnerability, crash on startup
2. **Performance Regression** - >50% slowdown in core operations
3. **Compatibility Break** - v1.2.1 tests fail in v1.3.0
4. **Widespread Failures** - >10% of users report same issue

**Who can trigger:**
- Project lead
- Release manager
- On-call engineer (if production incident)

### 8.2 Rollback Procedure

**v1.3.0 is 100% backward compatible** - Rollback is LOW RISK.

**Step 1: Revert Installation**
```bash
# Homebrew
brew uninstall clnrm
brew install clnrm@1.2.1

# Cargo
cargo uninstall clnrm
cargo install clnrm --version 1.2.1

# Docker
docker pull clnrm:1.2.1
```

**Step 2: Verify v1.2.1 Works**
```bash
clnrm --version  # Should show 1.2.1
clnrm self-test  # Should pass
```

**Step 3: Remove v1.3.0 Config (Optional)**
```bash
# Remove [weaver] sections from TOML files
find . -name "*.clnrm.toml" -exec sed -i '/^\[weaver\]/,/^$/d' {} \;
```

**Step 4: Notify Users**
- GitHub release note: "v1.3.0 rolled back to v1.2.1 due to [reason]"
- Discord announcement
- Email to beta testers

**Step 5: Root Cause Analysis**
- Incident report: What went wrong
- Fix plan: Timeline for v1.3.1
- Testing gaps: What we missed

## 14. Appendix B: Key Decision Records

### ADR-001: Type-Safe State Machine for Orchestration

**Decision:** Use PhantomData<State> to enforce orchestrator lifecycle at compile time.

**Rationale:**
- Prevents calling stop() on unstarted orchestrator (compile error, not runtime panic)
- Clear ownership model (state transitions consume and return new types)
- Self-documenting API (function signatures show valid transitions)

**Alternatives Considered:**
- Runtime state tracking (error-prone, requires runtime checks)
- No state machine (easy to misuse API)

**Status:** APPROVED

---

### ADR-002: Atomic Port Locking with File-Based Locks

**Decision:** Use flock (Unix) and LockFileEx (Windows) for port coordination.

**Rationale:**
- OS-enforced atomicity (no race conditions)
- Automatic cleanup on crash (OS releases locks)
- Cross-process coordination (works even across unrelated processes)
- Standard approach (used by systemd, Docker, PostgreSQL)

**Alternatives Considered:**
- Database-based coordination (too heavy, external dependency)
- Port reservation service (complex deployment, single point of failure)
- Fixed port allocation (inflexible, doesn't scale)

**Status:** APPROVED

---

### ADR-003: 80/20 Mode as Default for CI/CD

**Decision:** Make 80/20 validation mode the default for CI/CD pipelines.

**Rationale:**
- 6x faster than strict mode (5s vs 30s)
- Catches 80%+ of production bugs
- Fast feedback loop for developers
- Strict mode still available for release gates

**Alternatives Considered:**
- Strict mode default (too slow for CI/CD)
- Lenient mode default (misses critical bugs)

**Status:** APPROVED

---

### ADR-004: 100% Backward Compatibility (No Breaking Changes)

**Decision:** v1.3.0 is fully backward compatible with v1.2.1. All existing TOML files work unchanged.

**Rationale:**
- Weaver validation is opt-in (disabled unless `[weaver]` section present)
- Zero migration effort for existing users
- Risk-free upgrade path
- Maintains trust with user base

**Alternatives Considered:**
- Breaking changes (faster innovation but breaks trust)

**Status:** APPROVED

## 15. Appendix C: Glossary

- **80/20 Validation:** Focus on critical 20% of telemetry providing 80% of validation value
- **Atomic Locking:** Indivisible operation preventing race conditions (flock)
- **Conformance Report:** Weaver output validating telemetry against schemas
- **Critical Span:** Span that cannot be faked, proves core feature works
- **False Positive:** Test passes but feature doesn't actually work
- **Live-Check:** Weaver mode validating real-time telemetry streams
- **OTLP:** OpenTelemetry Protocol (telemetry export standard)
- **PhantomData:** Rust type for compile-time state tracking (zero runtime cost)
- **RAII:** Resource Acquisition Is Initialization (automatic cleanup)
- **Type-Safe State Machine:** State machine enforced at compile time (not runtime)
- **Weaver:** OpenTelemetry schema validation tool
- **Weaver-First:** Start Weaver before OTEL initialization (coordination pattern)
- **Zero-Sample Detection:** Failing validation if no telemetry received (catches false positives)
